# Файловые системы на сервере: как читать `df -h`

Разбор вывода `df -h` с сервера, где развёрнут этот проект (VPS с диском 50 ГБ), от 2026-11-02.

**Коротко:** настоящий диск один — `/dev/sda1` на 50 ГБ, занято 20 ГБ, свободно 31 ГБ.
Строки `tmpfs` — это оперативная память, а не диск. Строки `overlay` — файловые системы
контейнеров Docker, которые лежат на том же `/dev/sda1`. Их нельзя складывать с диском:
это одно и то же место, показанное несколько раз.

## Колонки

```
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        50G   20G   31G  39% /
```

| Колонка | Что значит |
|---|---|
| Filesystem | откуда данные: устройство (`/dev/sda1`) или тип виртуальной ФС (`tmpfs`, `overlay`) |
| Size | общий размер |
| Used | занято |
| Avail | доступно обычным пользователям |
| Use% | `Used / (Used + Avail)`, округлено вверх |
| Mounted on | каталог, в котором видна эта файловая система |

Почему 20 + 31 ≠ 50: ext4 по умолчанию резервирует 5% диска (около 2,5 ГБ) для root,
чтобы система продолжала работать, даже когда пользователи заполнили диск.
Эти 5% не входят ни в Used, ни в Avail. Ещё немного съедают служебные структуры ФС и округление.

## Строки по типам

### `/dev/sda1` — настоящий диск

Единственный физический (точнее, виртуальный диск VPS) раздел, смонтирован в корень `/`.
На нём лежит всё: система, `/opt/jitsi-meet`, `/opt/jitsi-meet-cfg` (конфиги и записи Jibri),
`/opt/jitsi-file-sharing/uploads` (файлы из чата) и `/var/lib/docker` (образы и контейнеры).

Свободного места в нём и надо следить.

### `tmpfs` — файловые системы в оперативной памяти

`tmpfs` хранит файлы в RAM (при нехватке памяти — в swap). После перезагрузки содержимое пропадает.
Размер — это верхний предел, а не занятая память: пустой tmpfs памяти не расходует.

| Точка монтирования | Размер | Зачем |
|---|---|---|
| `/run` | 392M | состояние работающей системы: PID-файлы, сокеты (`docker.sock`), данные systemd |
| `/dev/shm` | 2.0G | общая память между процессами (POSIX shared memory); её используют браузеры, базы данных |
| `/run/lock` | 5.0M | файлы блокировок, чтобы две программы не делали одно и то же одновременно |
| `/run/user/0` | 392M | временный каталог пользователя с uid 0 (root). Создаётся systemd при входе по SSH и удаляется после выхода |

По этим размерам видно, сколько на сервере памяти: systemd по умолчанию отдаёт `/run` и `/run/user/*`
10% RAM, а `/dev/shm` — 50%. 392M и 2.0G дают около **3,9 ГБ RAM**. Точно можно посмотреть командой `free -h`.

### `overlay` — файловые системы контейнеров Docker

У каждого **запущенного** контейнера есть своя корневая ФС: в выводе это одна строка `overlay`,
смонтированная в `/var/lib/docker/overlay2/<id>/merged`. У тебя таких строк 11 — значит,
работают 11 контейнеров.

Как устроен overlay:

```
merged  ← то, что видит процесс в контейнере как "/"
  ├── upperdir  — изменения этого контейнера (записанные файлы), свой у каждого контейнера
  └── lowerdir  — слои образа, только для чтения, общие для всех контейнеров из этого образа
```

Все эти каталоги лежат в `/var/lib/docker` на `/dev/sda1`. Поэтому у каждой строки `overlay`
те же 50G / 20G / 31G, что и у `/`: `df` показывает диск, на котором эта ФС физически лежит.
Это **не** дополнительные 11 × 50 ГБ.

Откуда 11 контейнеров:
- Jitsi (compose-проект `jitsi`): `web`, `prosody`, `jicofo`, `jvb`, `jibri` — 5;
- обмен файлами (`jitsi-file-sharing`): `file-sharing` — 1;
- остальные 5 — другие сервисы на сервере, например Nginx Proxy Manager. Список: `docker ps`.

Данные, которые Jitsi и сервис файлов пишут в смонтированные каталоги (`/opt/jitsi-meet-cfg`,
`/opt/jitsi-file-sharing/uploads`), идут не в `upperdir`, а прямо на `/dev/sda1`: это bind mount.
Поэтому они сохраняются, даже если контейнер пересоздать.

## Полезные команды

| Задача | Команда |
|---|---|
| Только настоящие диски, без tmpfs и overlay | `df -h -x tmpfs -x overlay -x devtmpfs` |
| Показать тип ФС | `df -hT` |
| Свободные inode (файлов может не хватить раньше, чем места) | `df -i /` |
| Сколько занимает Docker: образы, контейнеры, тома, кэш сборки | `docker system df` |
| Что занимает место в каталогах | `du -sh /var/lib/docker /opt/* 2>/dev/null \| sort -h` |
| Размер файлов из чата | `du -sh /opt/jitsi-file-sharing/uploads` |
| Размер записей Jibri | `du -sh /opt/jitsi-meet-cfg/storage/jibri/recordings` |
| Какие контейнеры запущены | `docker ps --format '{{.Names}}\t{{.Image}}'` |
| Память | `free -h` |

## Что это значит для обмена файлами

- Лимит `jitsi_file_sharing_max_total_size_gb: 5` помещается с запасом: после его заполнения
  на диске останется около 26 ГБ.
- Старые образы после обновлений Jitsi остаются в `/var/lib/docker` и занимают место.
  Посмотреть: `docker system df`, удалить неиспользуемые: `docker image prune -a`
  (удалит все образы, у которых нет контейнеров; при следующем деплое они скачаются снова).
- Записи конференций Jibri (`/opt/jitsi-meet-cfg/storage/jibri/recordings`) очищаются автоматически:
  по сроку и общему объёму (`jitsi_recordings_retention_days`, `jitsi_recordings_max_total_size_gb`).
